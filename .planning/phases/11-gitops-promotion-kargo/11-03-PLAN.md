# Plan 11-03: Jenkins CI Pipeline & E2E Verification (microservices-demo)

## Objective
Set up the Jenkins CI pipeline (`Jenkinsfile.demo`) for the Google microservices-demo (Online Boutique) to update Helm chart image tags and commit to the GitOps repo. Add Keycloak client and RBAC documentation to `docs/ADR-001-platform-auth-rbac.md`, configure Jenkins Job DSL for the pipeline, and perform end-to-end verification of the full promotion flow.

## Must Haves
- Jenkins pipeline `apps/microservices-demo/Jenkinsfile.demo` updates the Helm values file (`manifests/apps/microservices-demo/uat/values.yaml`) with new image tags for all 10 services, commits and pushes to `main`.
- Use upstream pre-built images from `gcr.io/google-samples/microservices-demo` with tag overrides — no need to build images locally (simpler, faster, demonstrates tag-based promotion).
- Jenkins JCasC jobs block in `manifests/bootstrap/jenkins/values.yaml` registers the `microservices-demo` pipeline using Job DSL.
- Update `docs/ADR-001-platform-auth-rbac.md` with Kargo OIDC client configuration and groups-to-roles RBAC mappings.
- Fully verify end-to-end promotion flow: Jenkins → Git commit → Kargo Freight → UAT auto-deploy → DevOps manual PROD promote.

### Prohibitions
- Do not use static/hardcoded credentials for Jenkins JNLP agents or Kaniko builders (must use Workload Identity).
- Do not push JNLP agent containers to the system node pool.
- Do not authorize the Keycloak developers group to approve PROD promotions.

## Verification
1. Verify Jenkins job registration:
   - Access `https://jenkins.smapatticare.com`.
   - Log in using Keycloak credentials.
   - Verify `microservices-demo` pipeline job is created.
2. Trigger the CI build:
   - Run the `microservices-demo` pipeline build.
   - Check build logs to ensure Helm values file is updated with new image tag.
   - Verify the git commit is pushed to the repo.
3. Verify Freight creation:
   - Access Kargo CLI or UI.
   - Run `kubectl get freight -n microservices-demo` to ensure Kargo has detected the commit and created a new Freight.
4. Verify Auto-Promotion to UAT:
   - Check that `microservices-demo-uat` ArgoCD Application updates the target commit and syncs.
   - Run `kubectl get pods -n demo-uat` and verify all 10 services are running with the new image tag.
5. Verify PROD Promotion Gate:
   - Log in to Kargo UI at `https://kargo.smapatticare.com` as a user in the `developers` group (e.g. `dev@smapatticare.com`).
   - Attempt to promote the UAT Freight to PROD. Verify access is denied/restricted.
   - Log in as a user in the `devops` group (e.g. `devops@smapatticare.com`).
   - Click "Promote" on the UAT Freight, select the PROD stage, and confirm.
   - Verify that Kargo triggers the promotion step, updating `microservices-demo-prod` application, and pods in `demo-prod` namespace restart with the new version.

## Threat Model
<threat_model>
- **Threat:** Git credential leakage from Jenkins JNLP build agents.
  - **ASVS Control:** V2.10.3 (Secret Storage / Kubernetes mounts).
  - **Mitigation:** Use Jenkins credentials provider and Workload Identity annotation to authenticate JNLP agents to ACR/Git without persistent static secrets.
- **Threat:** Container image spoofing or poisoning in ACR.
  - **ASVS Control:** V1.11.1 (Verification / Supply chain security).
  - **Mitigation:** Enforce Workload Identity federation on JNLP build pods so that only authorized, ephemeral containers spawned by Jenkins can push to the ACR repository.
- **Threat:** Unauthorized access to Keycloak client configuration or redirect URIs.
  - **ASVS Control:** V1.2.2 (OIDC configuration security).
  - **Mitigation:** Document client specification in ADR-001. Ensure OIDC client is restricted to secure callback URLs (`https://kargo.smapatticare.com/auth/callback`) to prevent token leakage.
</threat_model>
